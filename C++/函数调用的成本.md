# 函数调用的成本（function call overhead）

> 一句话：函数调用就像找同事帮忙——走过去、把数据交给他、等他算完、再走回自己工位，这些动作都要花时间。调用的次数多了、搬的数据大了、同事工位不确定，成本就上来了。
>
> 本篇是 [[内联函数]] 第 1 节的展开：内联函数省掉的，就是这些成本。

## 0. 先给结论（没耐心可只看这里）

1. **函数调用本身不算慢**：一次「已被预测」的直接调用大约只要几个 CPU 周期（1～2 纳秒）。
2. **真正贵的是附带动作**：大对象按值传参的拷贝、构造与析构、保存和恢复寄存器。
3. **更隐蔽的是编译器不敢优化了**（优化屏障）：调用前后寄存器里的值要写回内存，循环里的调用还会阻止向量化。这是内联在热点代码里最大的收益。
4. **间接调用**（函数指针、虚函数）除了多一次查表跳转，还可能让分支预测失败（一次约 15～20 个周期），并且通常无法内联。
5. **结论**：热点路径上的小函数值得内联；冷路径、偶尔调用的函数不用操心。优化前先 profile。

## 1. 一次调用发生了什么（白话版）

先解释三个词，后面会反复用到：

- **寄存器**：CPU 内部几个超快的小格子，算术运算和参数传递优先走它；
- **栈**：每个函数临时使用的内存区，函数返回时整块丢弃；
- **栈帧**：一个函数在栈上占的那块地。

用「找同事帮忙算数」来类比：

| 步骤 | 生活场景 | 程序里 |
| --- | --- | --- |
| ① | 你把数字写在纸条上递给他 | 把参数放进寄存器（放不下就放栈上） |
| ② | 你走到他的工位 | `call` 跳转，同时记住回来的位置（返回地址） |
| ③ | 他收拾桌面、腾出地方 | 建立栈帧，保存自己会用到的寄存器 |
| ④ | 他开始计算 | 执行函数体 |
| ⑤ | 他把结果给你，你走回工位 | `ret` 返回；返回值放在寄存器（如 `rax`）里 |

示意：

```
调用方                                  被调函数
  │ ① 准备参数                           │
  ├────────────── call ───────────── ──►│ ② 保存现场、建立栈帧
  │                                     │ ③ 执行函数体
  │◄───────────── ret ───────────── ────┤ ④ 恢复现场、销毁栈帧
  │ ⑤ 从寄存器读返回值                    │
```

这几步一共产生四类成本：**跳转**、**参数搬运**、**现场保存恢复**、**返回值搬运**。下面逐个看哪类最贵。

## 2. 成本清单：钱都花在哪

### 2.1 调用本身：其实不贵

- 直接调用 = 一条 `call` 指令跳到目标 + 一条 `ret` 跳回来；
- 目标地址是写死的，CPU 的分支预测器能轻松预测，一次大约 2～5 个周期；
- 换算一下：每秒调用 100 万次，花在跳转上的时间大约只有 2 毫秒——基本可以忽略；
- 所以「函数调用慢」时，通常不是慢在这两条跳转指令上。

### 2.2 参数搬运：小参数免费，大参数要命

- `int`、指针、`double` 这类小参数：直接放寄存器，相当于递一张纸条，几乎免费；
- 大结构体按值传（比如 `struct Big { int data[1024]; }`，4 KB）：每次调用都要复制一份，等于每次搬一箱书；
- `std::string` 按值传：除了复制内容，还要构造、析构；内容长时还会**堆分配**（向系统申请内存），那比寄存器慢几个数量级；
- 对策：只读的大对象用 `const T&`（只传地址，像给同事一张写着「数据在 3 号柜」的纸条）；确实需要拷贝/移动语义时才按值传；
- 反过来，小对象（`int`、两个 `int` 的 `pair`）按值传往往更快——它们能一直待在寄存器里，不用解引用。

### 2.3 现场保存：函数要先把自己的东西收好

- CPU 的寄存器是公共资源：A 函数正用着 `rbx`，调用 B 之后 `rbx` 可能被 B 改掉；
- 所以每个函数都遵守约定：用之前先保存（`push`），用完再恢复（`pop`）；
- 函数越小，这几条保存/恢复指令占比越高——这也是内联小函数收益明显的原因之一。

### 2.4 返回值搬运：结果也得拿回来

- 小结果（`int`、指针）：直接放寄存器，免费；
- 大结果（大结构体）：调用方要提前准备好一块内存放结果，并把它的地址告诉被调函数（这叫 `sret`，结构体返回），相当于让同事「把结果写在你给的本子上」；
- 返回值优化（RVO/NRVO）：编译器会直接把对象构造在最终位置，省掉这次复制；C++17 起，对纯右值返回的复制省略是**语言保证**的。

### 2.5 隐藏的大头：编译器不敢优化了（优化屏障）★

这条最重要，也最不直观。

编译器编译到 `call` 时**不知道被调函数会干什么**：它可能修改全局变量，也可能修改某个指针指向的内存。为了保证正确性，编译器必须做最坏的打算：

- **把寄存器里还要用的值写回内存**（叫 spill），调用返回后再重新读回来；
- 于是很多优化做不了了：常量传播、公共子表达式消除、循环向量化、死代码消除……

```cpp
int total = 0;
for (int i = 0; i < n; ++i)
    total += get_value(i);   // 若 get_value 未被内联，每次循环都要：
                             // 把 total 写回内存 → call → 再把 total 读回来
```

如果 `get_value` 被内联，函数体就直接摆在眼前，编译器知道它没乱改内存，`total` 可以一直住在寄存器里，循环甚至能被向量化（一次算好几个）。

所以记住：**内联最大的收益不是省掉那条 `call`，而是让编译器「看穿」函数体，解锁后续优化。**

生活类比：每次找同事帮忙，你回来都得重新确认桌上东西有没有被动过；如果活就在你旁边顺手干完（内联），就不用反复确认了。

## 3. 什么情况下「特别贵」

### 3.1 间接调用：函数指针、虚函数

- **直接调用**：`call` 后面直接写着目标地址——像你知道同事坐在哪；
- **间接调用**：地址要运行时去查——像到前台问「这项活今天谁负责」；
- **虚函数**：先读对象的 `vptr`（指向虚表的指针）→ 再读虚表里第 i 项 → 才拿到函数地址。多两次内存读，外加一次「猜目标」的跳转；
- 分支预测器猜错一次，代价约 15～20 个周期，比一次调用本身还贵好几倍；
- 更麻烦的是：**间接调用通常无法内联**，于是 2.5 的优化屏障也会一起出现。

### 3.2 其他常见「附加费」

| 场景 | 为什么贵 |
| --- | --- |
| 大对象按值传参 / 返回 | 复制、构造、析构，可能伴随堆分配 |
| 临时 `std::string` | 每次调用都构造 + 析构，内容长还要申请内存 |
| `throw` 抛异常 | 栈展开、匹配异常类型、析构局部对象，微秒级；正常路径几乎免费 |
| 调用动态库函数 | 经过 PLT/GOT 间接跳转，首次调用还要解析符号 |
| 系统调用（`read`/`write`） | 要陷入内核，比函数调用贵上千倍 |
| Debug 构建（`-O0`） | 不内联、变量全放内存，所有成本被放大 |

## 4. 内联为什么能省：回看清单

对照第 2 节的四类成本：

| 成本 | 内联之后 |
| --- | --- |
| `call`/`ret` 跳转 | 消失，函数体直接出现在调用点 |
| 参数搬运 | 常被优化掉，参数直接参与计算 |
| 现场保存 | 不再需要为独立函数保存寄存器 |
| 返回值搬运 | 结果直接落在目标位置 |
| 优化屏障 | 消失，编译器可以继续常量传播、向量化 |

代价：代码体积变大（重复展开）、编译变慢、调试断点变难。所以「小、热、简单」的函数才适合内联，大函数交给编译器自己判断。详见 [[内联函数]]。

## 5. 量级速查表（建立直觉用）

> 以下是现代 x86-64 CPU 的**粗略数量级**，用于感受差距，不要当基准测试结果。

| 操作 | 粗略成本 |
| --- | --- |
| 寄存器运算（`add`/`mov`） | 约 1 个周期 |
| 直接调用（已正确预测） | 约 2～5 个周期（不含函数体） |
| 间接调用预测失败 | 额外 15～20 个周期 |
| L1 缓存命中 | 约 4～5 个周期 |
| 主存访问（缓存未命中） | 约 200～300 个周期 |
| 堆分配（`malloc`/`new`） | 几十到几百个周期 |
| 系统调用 | 数百纳秒以上 |
| 线程上下文切换 | 微秒级 |

反直觉的一点：**冷调用可能被一两次缓存未命中完全支配**，而跳转指令本身只有几个周期。所以「函数调用慢」必须结合调用频率和数据大小来看。

## 6. 面试 / 复习怎么答

| 问题 | 参考回答 |
| --- | --- |
| 函数调用的过程？ | ① 参数放入寄存器/栈 → ② `call` 压入返回地址并跳转 → ③ 被调函数保存现场、建立栈帧 → ④ 执行函数体 → ⑤ `ret` 恢复现场返回，结果放在寄存器里 |
| 函数调用有哪些开销？ | 跳转本身、参数搬运、保存/恢复寄存器、返回值搬运；更大的隐性开销是调用让编译器无法跨调用优化（寄存器 spill、无法向量化） |
| 为什么内联函数快？ | 省掉 `call`/`ret`、参数搬运和栈帧；更重要的是把函数体暴露给编译器，解除优化屏障，可能触发常量传播与向量化。`inline` 只是建议，不保证展开 |
| 虚函数调用为什么慢？ | 通过 `vptr` → `vtable` 间接调用：多两次内存读、目标可能预测失败，且通常无法内联（连带优化屏障） |
| 大对象传参用值还是 `const` 引用？ | 只读用 `const T&` 避免拷贝；小对象按值更好（寄存器传递）；需要拷贝/移动语义时才按值 |
| 怎么测量函数调用开销？ | 先 profile 找热点，再做微基准（Google Benchmark）；用 `DoNotOptimize` 防止被优化掉；不要用 Debug 构建下结论 |

## 7. 进阶：想深入时再看（基础读者可跳过）

### 7.1 汇编对照

```cpp
int add(int a, int b) { return a + b; }
int caller(int x) { return add(x, 42); }
```

`-O0`（未优化，示意）：

```asm
caller:
        push    rbp
        mov     rbp, rsp
        sub     rsp, 16
        mov     DWORD PTR [rbp-4], edi    ; 参数 x
        mov     eax, DWORD PTR [rbp-4]
        mov     esi, 42                   ; 第二个参数
        mov     edi, eax                  ; 第一个参数
        call    add
        leave
        ret
```

`-O2`（已内联，跳转/栈帧/参数搬运全部消失）：

```asm
caller:
        lea     eax, [rdi+42]      ; 直接算出 x + 42
        ret
```

### 7.2 ABI：参数和返回值放哪

| 平台 | 整数/指针参数 | 浮点参数 | 返回值 |
| --- | --- | --- | --- |
| x86-64 System V（Linux/macOS） | `rdi, rsi, rdx, rcx, r8, r9`（前 6 个） | `xmm0`–`xmm7` | `rax`；大对象用隐藏指针 |
| Windows x64 | `rcx, rdx, r8, r9`（前 4 个） | `xmm0`–`xmm3` | `rax`（大对象同样用隐藏指针） |
| ARM64 | `x0`–`x7` | `v0`–`v7` | `x0` |

寄存器不够用时，多余参数才压栈。

### 7.3 栈帧、red zone、对齐

- x86-64 SysV 要求调用时栈 16 字节对齐（`call` 压入 8 字节返回地址），编译器会插入填充；
- `rbp` 作帧指针方便调试，`-O2` 通常省略（`-fomit-frame-pointer`）；
- **red zone**：System V ABI 允许叶子函数（不再调用别人的函数）直接使用 `rsp` 往下 128 字节，无需 `sub rsp`；Windows x64 没有这个概念。

### 7.4 sret 与 RVO

- 大对象返回时，调用方分配空间并把地址作为隐藏参数传入（`sret`），被调函数在那块内存里构造对象；
- 小聚合（≤16 字节）在某些 ABI 下可用两个寄存器返回（如 `rax:rdx`）；
- RVO 让「返回临时对象」不产生额外拷贝；C++17 起纯右值返回的复制省略是强制的，NRVO 仍由编译器决定。

### 7.5 去虚化与 `std::function`

- 编译器在能确定动态类型时会「去虚化」（`final` 类/方法、LTO、PGO），把虚调用变成直接调用甚至内联；
- `std::function` 是类型擦除容器：内部存小对象缓冲 + 函数指针（或虚表），捕获对象大时会**堆分配**，每次调用还多一层间接——性能敏感时优先模板参数或 `auto` lambda。

### 7.6 怎么测量

- 先 `perf record`（或 VTune）找热点，再写微基准；不要只凭直觉优化；
- 防止循环被优化掉：把结果累加，最后用编译器屏障「用一下」结果；
- 看反汇编确认是否真的内联：`objdump -d` 或 godbolt.org；
- 注意 Turbo Boost、线程迁移、分支预测「热身」等干扰；Debug 构建的数字无效。

## 8. 小结

- 一次调用 = 参数搬运 + `call` + 栈帧/寄存器保存 + `ret`；已预测时本身只需几个周期；
- 真正的大头：优化屏障（spill、无法跨调用优化）、按值拷贝、间接调用预测失败、缓存未命中；
- 大对象只读传 `const&`，小对象按值即可；需要拷贝/移动语义时才按值；
- 虚函数、函数指针、`std::function` 的成本主要来自间接跳转与无法内联；
- 优化顺序：算法/数据结构 → 减少拷贝和临时对象 → 热点小函数内联 → 减少间接调用 → 微观指令。
